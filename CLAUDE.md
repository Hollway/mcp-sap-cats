# mcp-sap-cats

MCP-сервер для таймшитов SAP (транзакция CAT2 / CATS). Задача трекера — **SAP-18862 «MCP для CAT2»**, срок 01.10.2026.

Проект выделен из общего чата 21.09.2026. Техническое решение и оценка согласованы, см. `docs/solution.md`.

## Что это

Node/TypeScript MCP-сервер, который ходит в SAP не напрямую, а через собственный ICF-хендлер на стороне ABAP. Хендлер вызывает стандартные `BAPI_CATIMESHEETMGR_*`.

```
Claude  →  MCP (Node, этот репозиторий; stdio или HTTP)  →  HTTPS + Basic  →  ICF-узел SAP  →  BAPI_CATIMESHEETMGR_*
```

MCP-сервер запускается либо у каждого пользователя (stdio, логин SAP в его `.env`), либо одним общим сервером (`MCP_TRANSPORT=http`, логин приходит от клиента в каждом запросе) — см. «Доработки сверх ТЗ».

Целевая система — внутренний ERP-ландшафт компании (SID и хост намеренно не публикуются здесь), там же живут все ZMM_*/ZYTR_*.

## Текущее состояние (2026-09-24)

Узел SICF `/sap/bc/zcats` заведён и активен, обработчик — `ZCL_CATS_MCP_HANDLER` (пакет `ZCATS`, транспорт `<TRANSPORT_ID>`). Все маршруты — `/read`, `/validate`, `/insert`, `/change`, `/delete`, `/release`, `/capacity`, а с 2026-09-23 и `/whoami`, `/projects` — реализованы и проверены end-to-end через сам MCP-сервер, включая реальные коммиты. Первая рабочая запись через ключ задачи Трекера (`ext.ytr_key`) проведена 2026-09-23.

`/capacity` (2026-09-22) — единственный маршрут без BAPI: часы берутся прямым `SELECT ... GROUP BY workdate` из `CATSDB`, рабочий/нерабочий день определяется вызовом `DATE_CONVERT_TO_FACTORYDATE` с `FACTORY_CALENDAR_ID = 'BY'` на каждую дату диапазона (обёртка `DATE_CHECK_WORKINGDAY` не подошла — она сигнализирует нерабочий день через исключение, а `DATE_CONVERT_TO_FACTORYDATE` отдаёт `WORKINGDAY_INDICATOR` прямым полем, что проще в цикле по датам). `free = norm_hours - booked` в рабочий день, `0 - booked` в выходной/праздник. Проверено вживую (`cats_capacity`, PERNR 00099003, 2026-09-21): день с 4 часами из 8 отдал `free: 4`, с кастомной нормой 6 — `free: 2`; будни с полной выработкой (PERNR 00099001) — `free: 0`, выходные — `is_workday: false`.

`/validate` вызывает `BAPI_CATIMESHEETMGR_INSERT` с `TESTRUN = 'X'`. `receiver` из `schemas.ts` раскладывается в поля `BAPICATS1` веткой `IF/ELSEIF` по первому непустому полю (`map_receiver`); Z-поля из `ext` уходят в `EXTENSIONIN` через `BAPI_TE_CATSDB` — структура собирается через `VALUE #( )` и присваивается `VALUEPART1` прямым присвоением (стандартный приём для BAPI-расширений, компилятор об этом предупреждает — предупреждение ожидаемо и не блокирует активацию). Проверено вживую (`cats_validate`, PERNR 00099002, `receiver.cost_center` + `co_area`, `ext.prjct`): BAPI вернула настоящие построчные `BAPIRET2` (`KI101`, `FGV5`) с правильным `row`.

Побочная находка при тесте: PERNR 00099001 (табельный самого исполнителя) отдаёт `LR2` — «Транзакцию блокирует пользователь» — это реальная блокировка SAP (enqueue), не баг маршрута; на PERNR 00099002 тот же вызов проходит до BAPI без проблем.

`/insert` вызывает `BAPI_CATIMESHEETMGR_INSERT` с `TESTRUN = space` и сам коммитит (`BAPI_TRANSACTION_COMMIT` / `BAPI_TRANSACTION_ROLLBACK` в зависимости от `RETURN`) — коммит и роллбэк в одном обращении к хендлеру, как решено выше. Идемпотентность: `EXTSYSTEM='MCP'` / `EXTAPPLICATION='CATS'` (константы в классе) / `EXTDOCUMENTNO=idempotency_key` — перед вызовом BAPI хендлер сам ищет в `CATSDB` строки с тем же ключом (`SELECT` по тем же трём полям) и, если находит, возвращает их `COUNTER` без повторной записи.

**Найден и исправлен баг при первом же живом тесте:** `compress = abap_true` в `/ui2/cl_json=>serialize` вырезает не только пустой `row` в сообщениях, но и **весь массив `messages`, если он пуст, и `committed = false`** (ABAP считает initial-значение — включая `abap_false` — «пустым» и опускает поле). Из-за этого `cats_validate` при нуле ошибок уронил бы Node-сторону (`hasErrors(undefined)` дёргает `.some` на `undefined`), а `cats_insert` в первом тесте вернул `{}` вместо `{"created":[],"committed":false}`. `compress` убран из обоих маршрутов — `messages`/`created`/`committed` теперь всегда присутствуют в ответе, `row` для сообщений уровня всего вызова (без привязки к строке) будет приходить как `0`, а не отсутствовать.

**`/insert` подтверждён вживую полностью (2026-09-22).** Путь к этому: оба реальных набора данных с объектом отнесения (МВЗ+`co_area=BE01`, заказ `F0080232939`) уткнулись в незаведённый в системе вариант финансового года (`GP626`, `FGV5`, `LR68`) независимо от года записи (пробовал 2026 и 2025) — открытие `ZCL_YTRACKER_ZB_CATS_SERVICE` (см. ниже) показало, что реальный продовый код вообще не использует объект отнесения (`HRCOSTASG = '0'`), поэтому `receiver` в `schemas.ts` сделан необязательным. После этого — `cats_insert` без `receiver`, только `ext.prjct` с реальным активным проектом (`ZBTPRJCT-ACTIVE = 'X'`, найден `BASIS`) — прошёл первым настоящим коммитом: `committed: true`, `counter: "000000388371"`, запись подтверждена прямым `SELECT` из `CATSDB` (PERNR 00099002, 2026-09-15, 2ч, `ZZPRJCT=BASIS`, `EXTDOCUMENTNO=MCPTEST202609225`). Повтор с тем же `idempotency_key` вернул тот же `counter`, `committed: false`, сообщение `S`/`MCP1` — задвоения нет, в базе одна строка.

**`/change`, `/delete`, `/release` реализованы и подтверждены вживую (2026-09-22).** Гипотезы прогнаны через `TESTRUN`/`runSnippet` перед кодом: `BAPI_CATIMESHEETMGR_CHANGE` требует полный ресенд записи, включая `EMPLOYEENUMBER`, — delta по одному `COUNTER` падает (`LR158`/`LR159`). `BAPI_CATIMESHEETMGR_DELETE` берёт только `COUNTER`. `/release` — тот же `BAPI_CATIMESHEETMGR_CHANGE` с `RELEASE_DATA = 'X'`, хендлер сам читает текущие значения строки из `CATSDB` (по `counter` или по `pernr`+период, только статус `10`) и ресендит их без изменений. Грабля при активации: `WHERE counter IN @itab` не компилируется для плоской `STANDARD TABLE OF catsdb-counter` («некорректная структура строки») — Open SQL `IN` требует range-таблицу (`TYPE RANGE OF catsdb-counter`), собранную уже после JSON-десериализации; сам JSON-контракт остался плоским массивом строк.

Живой прогон полного цикла (`cats_insert` → `cats_change` → `cats_release` → `cats_delete`, PERNR 00099001): **`cats_release` сразу даёт статус `30` «Утверждено», не `20`** — в `TCATS` для этих профилей `APPROVAL` пусто, процедура утверждения не настроена, промежуточного шага нет. Побочный эффект релиза: SAP сам пишет вторую строку в `CATSDB` (`REFCOUNTER` на исходный `COUNTER`, `HOURS = 0`) — штатная аудиторская история статуса, не баг хендлера; `cats_delete` на такую строку возвращает `committed: true` без сообщений, но ничего не меняет в БД (BAPI не даёт удалить историю). `cats_delete` на утверждённую запись (`30`) переводит её в `60` «Сторнировано» — строка остаётся, approval-статус удалению не мешает. **Запись, которая ни разу не утверждалась (`10`), SAP удаляет физически** вместе с `STXH` подробного текста (проверено 2026-09-24: строки нет ни в `CATSDB`, ни в `STXH`, `cats_read` пуст); прежнее «всегда `60`» было обобщением с одного случая статуса `30`.

Живые записи в SAP из этого MCP по умолчанию блокирует классификатор auto-режима Claude Code («Modify Shared Resources») — разрешено через `.claude/settings.local.json` (не в git, персонально для этой машины): `permissions.allow` с `mcp__sap-cats__cats_insert`/`cats_change`/`cats_delete`/`cats_release`. Файл создавал и заполнял сам пользователь — на запись в собственный файл разрешений классификатор блокирует и агента («Self-Modification»), это ожидаемо и обходить не стоит.

`.env` не читается автоматически: Claude Code запускает `node dist/index.js` напрямую, без загрузки `.env`. `loadConfig()` в `src/sap.ts` сам читает файл рядом с `dist/` (без внешней зависимости — `dotenv` не ставится там, где не проходит `npm install` за прокси).

**Доработки 2026-09-23 (ABAP + Node).**
- **Баг: сторнированные записи съедали норму.** Запись в статусе `60` сохраняет `CATSHOURS` (проверено на реальной сторнированной строке), а `check_daily_limit`, `/capacity` и `total_hours` в `/read` суммировали `CATSDB` без фильтра по статусу. Добавлена константа `c_status_cancelled` и `status <> '60'` во всех трёх местах; в `/read` сами строки статуса `60` по-прежнему выводятся.
- **Лимит в `/change`.** `check_daily_limit` получил необязательный `it_exclude` (плоская таблица `counter`): часы изменяемых записей вычитаются из уже записанных, чтобы изменение 2 → 10 ч проверялось как 10, а не 12. Сумма считается в ABAP по строкам (`SELECT counter, workdate, catshours` + `REDUCE` с `line_exists`), а не `NOT IN` по range: пустая range-таблица в `IN` означает «все строки», и `NOT IN` с пустой отдал бы ноль строк.
- **`/whoami`** — PERNR по `sy-uname` из `PA0105` (подтип `0001`), ФИО и оргединица из `PA0001` + `T527X`. Только собственная запись вызывающего, параметров нет.
- **`/projects`** — активные проекты (`ZBTPRJCT-ACTIVE = 'X'` + тексты `ZBTPRJCTT`), фильтр `search` (`CS`, без учёта регистра); с `prjct` — номера ТЗ из `ZBTPROJECT` (без `RQSDL`) с текстами `ZBTREQSPT`. Это тот же источник, что у матчкода `ZSRCH_CATS_RQSNB`.
- **Подробный текст.** `longtext` (строка) в записях `/validate`, `/insert`, `/change` → `BAPICATS8` (`split_longtext`: абзацы по переводу строки, куски по 132 символа, `*` — новый абзац, `=` — продолжение) + флаг `LONGTEXT` в `BAPICATS1`/`BAPICATS3`. `/read` отдаёт флаг `longtext` из `CATSDB` и сам текст в `longtext_text` (`read_longtext` → `longtext_to_string`: `*`/`/` — новый абзац, `=` — склейка, пробел — продолжение через пробел, `/:`/`/*` пропускаются; с 2026-09-23, проверено на записи из CAT2 с абзацем длиннее 132 символов). Текст хранится в SAPscript: объект `CATS`, ID `CATS`, имя = `COUNTER`, язык — из `STXH`.
- **Баг: `/release` стирал подробный текст — найден живым тестом и исправлен.** Ресенд строки в `BAPI_CATIMESHEETMGR_CHANGE` без `LONGTEXT` BAPI понимает как «текста нет»: флаг сбрасывается, `STXH` удаляется. Касалось и записей с текстом, заведённым в CAT2. Теперь `/release` читает текущий текст (`read_longtext`: `STXH` → `READ_TEXT`) и ресендит его вместе с флагом. Вторая грабля: `CHANGE` с непустым `LONGTEXT` без `TEXT_FORMAT_IMP` отвечает `LR360` «Текстовый формат  недействителен» (у `INSERT` параметр не нужен) — принимается только `'ITF'` (`ASC`/`RTF` — тоже `LR360`), константа `c_text_format` передаётся в `/change` и `/release`. Проверено вживую: запись с текстом → `cats_release` → статус `30`, флаг `X`, все три строки текста на месте.
- **Связка проект + номер ТЗ + описание, ключ задачи Трекера.** CAT2 делает это пользовательскими выходами CATS (пакет `ZCATS`), и они же срабатывают на пути через BAPI: `ZXCATU02` (обогащение) при пустом `ZZDESCR` и заданных проекте + номере ТЗ подставляет `ZBTREQSPT-RQSNM`, иначе `ZYTRPROJ-TASK_NAME`, и всегда пишет `ZZORGUNIT` из оргструктуры (`RH_STRUC_GET`, `P-S-O`); `ZXCATU05` (проверка) даёт `ZCATS001` при неактивном проекте. Существование пары и обязательность описания никто не проверяет — правило «без номера ТЗ описание вводят вручную» теперь проверяет схема MCP (`extFields.refine`). Новые ТЗ, заведённые из Трекера, живут в `ZYTRPROJ` (ключ `ID_YTR` = ключ задачи, `PROJECT`, `PROJECN`, `TASK_NAME`, `STATUS`, домен `ZYTR_STATUS`, `7` — удалено) и в старой `ZBTPROJECT` их нет; у `ZBTPROJECT` есть своё `YTR_KEY`, но у трёх ключей там по несколько пар. `/projects` принимает `ytr_key` (сначала `ZYTRPROJ`, потом `ZBTPROJECT`), а список ТЗ проекта объединяет обе таблицы с ключом и статусом задачи. `ext.ytr_key` в записях переводится в пару **на стороне Node** (`resolveYtrKeys`, через `/projects`) — маршруты записи в ABAP не менялись; неоднозначный, удалённый или противоречащий указанной паре ключ — ошибка до вызова SAP.
- **SAP сам пересортировал методы класса по алфавиту** (и сменил шапку на стиль SE24) после создания тестового инклуда. Номера строк из копии в репозитории после этого не совпадали с системой, и построчная правка упала на сохранении («The statement ZZRQSNB is unexpected»), ничего не записав. Копия в `abap/` синхронизирована с системой; **перед построчной правкой класса сверять номера строк с активной версией в системе, а не с копией.**
- **Регрессия, пойманная дампом в тот же день:** номер строки для `EXTENSIONIN` (`BAPI_TE_CATSDB-ROW`) брался из `sy-tabix` сразу после `APPEND ls_bapicats1`, а вставленный между ними `APPEND LINES OF split_longtext( ... )` без подробного текста сбрасывал `sy-tabix` в 0. BAPI на этом падает дампом `TABLE_INVALID_INDEX` в `SAPLBAPICATS` (`MAP2I_BAPICATS7_TO_CATS_EXT`, `READ TABLE catsrecords INDEX row`), причём уже на `TESTRUN`. Исправлено: `DATA(lv_row) = lines( ... )` (теперь внутри `build_insert_tables`/`build_change_tables`), проверено `cats_validate` без дампа. **Номер строки для `EXTENSIONIN`/`LONGTEXT` не брать из `sy-tabix`.**
- **ABAP Unit** — тестовый инклуд класса (копия — `abap/zcl_cats_mcp_handler.clas.testclasses.abap`, `LOCAL FRIENDS`): 17 методов на `map_receiver`, `time_from_hhmm`, `split_longtext`, `longtext_to_string`, `to_messages`, `has_errors`, `check_daily_limit` (на несуществующем PERNR `99999999` и дате `9999-12-30`, поэтому `HARMLESS`), `build_insert_tables`/`build_change_tables`. Все проходят. Сам вызов BAPI не покрыт, но сборка таблиц для него — да: тесты проверяют, что `ROW` в `EXTENSIONIN` и `LONGTEXT` совпадает с индексом записи, в том числе когда у записи в середине нет подробного текста (случай регрессии с `row = 0`).
- **Сборка данных для BAPI вынесена в общие методы (2026-09-23, бэклог закрыт).** `build_insert_tables` (для `/validate` и `/insert`; `idempotency_key` необязателен — без него `EXTSYSTEM`/`EXTAPPLICATION`/`EXTDOCUMENTNO` не заполняются, как раньше в `/validate`) и `build_change_tables` (для `/change`) возвращают структуру `catsrecords` + `extensionin` + `longtext`. `/release` собирает данные сам — из строк `CATSDB` и `read_longtext`. Проверено вживую: `cats_validate` (3 записи, у средней нет текста), `cats_change` с `test: true`; 2026-09-24 — полный цикл `cats_insert` (с подробным текстом) → повтор с тем же `idempotency_key` (тот же `counter`, `committed: false`, `MCP1`) → `cats_read` (Z-поля, `ZZORGUNIT` и текст на месте) → `cats_delete`.
- **Список подчинённых — закрыт как выполненный (решение пользователя, 2026-09-23).** Требование ТЗ «свои либо подчинённых» закрыто полномочиями пользователя в BAPI (решение №2), отдельный инструмент со списком не делается.

**Надёжность и сценарии на Node-стороне (2026-09-23).** Таймаут `fetch` (`SAP_TIMEOUT_MS`, 60 с) и автоповтор ответа с `E`/`LR`/`002` (`SAP_LOCK_RETRIES`=2, пауза `SAP_LOCK_RETRY_DELAY_MS`×номер попытки) в `SapClient.call`. Повтор безопасен, потому что каждый пишущий маршрут делает ровно один вызов BAPI и коммитит или откатывает его целиком. Три MCP-prompts (`fill_week_like_last`, `fill_gaps`, `period_close_check`) только собирают вызовы инструментов и ничего не пишут без подтверждения пользователя. Сценарий «ворклоги Трекера → CATS» сознательно не сделан: разнесение часов по задачам трекера уже есть в `ZCL_YTRACKER_ZB=>CATS_UPDATE`, дублировать его нельзя.

**Дневной лимит часов реализован в MCP (2026-09-22).** `cats_validate`/`cats_insert` принимают `norm_hours` (по умолчанию 8) и блокируют запись, если существующие + новые часы за день превышают норму — через `check_daily_limit`, детали и найденный по пути баг двойного учёта — в «Открытые вопросы» ниже. Живой прогон полного цикла `cats_insert → cats_change → cats_release → cats_delete` на PERNR 00099001 в тот же день подтвердил отсутствие регрессий: `cats_release` даёт статус `30` сразу (как и раньше), `cats_delete` штатно ловил `LR2` (блокировка своей же транзакции) и прошёл со второй попытки без вмешательства в код — совпадает с ранее задокументированным поведением на другом PERNR.

**Приёмка 2026-09-23: правка утверждённой записи и статус 50.** Прогон на своём табельном (`cats_insert` с `release` → `cats_change` → `cats_delete`): утверждённую запись (`30`) `BAPI_CATIMESHEETMGR_CHANGE` на месте не правит — создаёт новую версию в статусе `10` с новым `COUNTER` (хендлер возвращает его в `changed`), старая уходит в `50` «После утверждения изменено» **с прежними часами**. Запись в `50` BAPI менять не даёт (`LR162`). Удаление новой версии сторнирует и её, и исходную (`50` → `60`), а SAP оставляет строку-историю `30` с нулём часов. Прежнее описание «30 и 50 изменению не подлежат» было неверным (такой проверки в коде и не было) — исправлено в `cats_change` и в prompt `period_close_check`.
**Баг, найденный этим прогоном и исправленный в тот же день:** статус `50` считался живыми часами в `check_daily_limit`, `/capacity` и `total_hours` `/read` — после правки 1 → 2 ч день показывал 3 ч. Добавлена константа `c_status_changed`, `50` исключён во всех трёх местах так же, как `60` (`status NOT IN ( @c_status_changed, @c_status_cancelled )`). Проверено повтором цикла: `booked: 2`, `total_hours: 2`, `cats_validate` на +6 ч проходит; ABAP Unit — 12 из 12.

**Доработки сверх ТЗ (2026-09-24).**

## Решения, которые уже приняты — не переоткрывать

1. **Канал — ICF-хендлер, не `node-rfc`.** BAPI RFC-включены, но `node-rfc` требует SAP NW RFC SDK и сборки нативного модуля за корпоративным прокси. Хендлер дешевле и даёт единую точку логирования.
2. **Узел SICF заводится без сохранённых данных логона.** Каждый запрос несёт `Authorization: Basic`, SAP авторизует реального пользователя. Круг доступных табельных номеров определяют его `P_ORGIN` и структурная авторизация — ровно как в CAT2. Требование ТЗ «свои либо подчинённых» закрывается конфигурацией, без логики в MCP.
   **Служебный пользователь с широкими правами в данных логона узла недопустим** — он снимает проверки и обезличивает записи.
3. **Запись только через BAPI, не прямым INSERT в `CATSDB`.** Прямая запись обходит проверки профиля, BAdI `ZCL_BADI_CATS` и нумерацию `COUNTER`. Чтение из `CATSDB` — наоборот, штатный путь.
4. **OData отклонён.** Стандартного OData-сервиса для CATS в ERP нет; ближайшее — enterprise service (SOAP + SOAMANAGER), без выигрыша.
5. **`BAPI_TRANSACTION_COMMIT` вызывается внутри того же обращения к хендлеру**, что и сама BAPI. При stateless HTTP каждый запрос — новая LUW, и запись пропадёт молча.
6. **Идемпотентность через `EXTAPPLICATION` / `EXTDOCUMENTNO` / `EXTSYSTEM`.** У BAPI нет своего ключа идемпотентности; без этого повторный вызов при обрыве связи задваивает часы.
7. **Чтение (`/read`, `/capacity`) полномочия не проверяет — так и оставлено (решение пользователя, 2026-09-23).** Читать можно любой табель; ограничение «свои либо подчинённых» действует только на запись, где его проверяет сама BAPI. Стандартная проверка чтения, если когда-нибудь понадобится, — `CATS_CHECK_AUTHORITY` с `ACTION = 'R'` (внутри `HR_CHECK_AUTHORITY_INFTY`, ИТ `0328`), как в `BAPI_CATIMESHEETRECORD_GETLIST`.

## Факты о системе, проверенные запросами

- `BAPI_CATIMESHEETMGR_INSERT` / `_CHANGE` / `_DELETE` и `BAPI_CATIMESHEETRECORD_GETLIST` — все RFC-включены (`TFDIR-FMODE = 'R'`).
- У INSERT есть `PROFILE`, `TESTRUN`, `RELEASE_DATA`, `EXTENSIONIN`, табличный `CATSRECORDS_IN` (структура `BAPICATS1`, 78 полей), `LONGTEXT`, `RETURN`. DELETE берёт `BAPICATS4` по `COUNTER`.
- **`TESTRUN = 'X'` даёт полную валидацию по профилю без записи.** Дублировать проверки объектов отнесения в MCP не нужно.
- `CATSDB` расширена своим инклудом `CI_CATSDB`: `ZZRQSNB` («Номер ТЗ (п/п)», NUMC 5), `ZZPRJCT`, `ZZDESCR`, `ZZORGUNIT`. Структура `BAPI_TE_CATSDB` существует, то есть Z-поля пишутся через `EXTENSIONIN` штатно, доработка словаря не нужна.
- Домен `CATSSTATUS`: 10 в обработке · 20 деблокировано для утверждения · 30 утверждено · 40 утверждение отклонено · 50 после утверждения изменено · 60 сторнировано.
- Пакет `ZCATS`: BAdI `ZCL_BADI_CATS`, `ZCL_IM_CATS_REPORTING`, матчкод `ZSRCH_CATS_RQSNB`, класс сообщений `ZCATS`.

## Профили ввода данных — здесь главные подвохи

`TCATS`, ключ = MANDT + **VARIANT** (не PROFILE): `TIME_D1`, `TIME_W1`, `TIME_M1`. У всех `DEFLGART = M120`, `FUTURE = 'X'`, `BRGRU` пусто, `PERNRLIST` пусто, `APPROVAL` пусто.

- **`PERLEFT`/`PERRIGHT` на `BAPI_CATIMESHEETMGR_INSERT` с `TESTRUN` не проверяются.** Опровергнуто прогоном: запись на 400 дней в прошлое (профиль `TIME_D1`) проходит `TESTRUN` без единого сообщения в `RETURN`. Ограничение из `TCATS`, если и действует, — на уровне диалоговой транзакции CAT2, а не в `CATS_EXTERNAL_INTERFACE`, который вызывает BAPI. **MCP через BAPI не окажется строже текущего кода** — вопрос записи за прошлые периоды закрыт, четвёртый профиль под это не нужен.
- **`MAXHRREACT`, `KOLHRREACT`, `OVERREACT` пусты, `OVERTARGET` = 0** → лимиты часов в день стандартом не проверяются вовсе. Требование ТЗ про лимиты — либо кастомайзинг профилей, либо свой расчёт по норме дня.
- `CUTOFFDT` и `PERLOCK` пусты. **Закрытых периодов в системе по сути нет** — пользователь подтвердил 2026-09-23, что CAT2 пускает вводить часы и за прошлый месяц, и за прошлый год. MCP (BAPI не проверяет `PERLEFT`/`PERRIGHT`) поэтому не мягче CAT2; своей проверки периодов в MCP не делаем, пункт ТЗ закрыт как «в системе не настроено».
- **`PERNRLIST` пусто → один вызов `BAPI_CATIMESHEETMGR_INSERT` не принимает вперемешку разные табельные номера.** Прогон с двумя разными `EMPLOYEENUMBER` в одном `CATSRECORDS_IN` вернул общую ошибку `LR199` («Используйте вариант регистрации для нескольких табельных номеров») ещё до проверки отдельных строк. Ввод за подчинённого работает (проверено на реальном табельном подчинённого — авторизация пропускает), но **MCP обязан группировать записи по `EMPLOYEENUMBER` и делать отдельный вызов BAPI на каждого сотрудника.**
- **BAdI `ZCL_BADI_CATS` требует непустой активный `ZZPRJCT`** (проверка по `ZBTPRJCT`) в каждой строке — без него `TESTRUN` возвращает `ZCATS001: Проект  не является активным` на весь вызов. `ext.prjct` в `schemas.ts` сделан обязательным (уже исправлено). Активность проекта проверяется по `ZBTPRJCT-ACTIVE = 'X'`, а не по самому факту существования строки в таблице — использованный при живом тесте `BASIS` активен, `SCM70` и тестовый `TESTPRJCT` — нет.

## Открытые вопросы

- ~~«Объект учёта — СПП-элемент / заказ / ВЗ»~~ — **решено 2026-09-22, подтверждено вживую.** `receiver` в `schemas.ts` стал необязательным. `ZCL_YTRACKER_ZB_CATS_SERVICE->cats_update` (существующий продовый код) вызывает `CATS_UPDATE` с `HRCOSTASG = '0'` и вообще не заполняет ни МВЗ, ни заказ — только Z-поля; попытки провести `cats_insert` через МВЗ/заказ раз за разом утыкались в CO-кастомайзинг (`GP626`/`FGV5`/`LR68`), а без `receiver` первый же прогон (PERNR 00099002, `ext.prjct=BASIS`) дал настоящий коммит (`counter 000000388371`, подтверждено `SELECT` из `CATSDB`).
- ~~Лимиты часов — кастомайзинг профилей или расчёт в MCP~~ — **решено и реализовано 2026-09-22.** Проверка в MCP (не кастомайзинг `TCATS`, чтобы не трогать общий профиль для всех пользователей CAT2). `check_daily_limit` считает уже записанные часы за день + новые из запроса, при превышении `norm_hours` (по умолчанию 8, параметр в `cats_validate`/`cats_insert`) добавляет `E`-сообщение (`MCP2`) в `lt_return` — тот же механизм commit/rollback, что и для ошибок самой BAPI, блокировку отдельно кодировать не пришлось.

  **Баг при первом живом тесте (не в проде, откат сработал):** изначально `check_daily_limit` вызывался *после* `BAPI_CATIMESHEETMGR_INSERT` — в `/insert` (не `/validate`, там `TESTRUN` не пишет) это давало двойной учёт: BAPI успевает физически вставить строку в `CATSDB` в той же LUW ещё до commit, и последующий `SELECT` внутри `check_daily_limit` видел собственную ещё не закоммиченную вставку. Пример: было 4ч, запрос на +6ч дал «уже 10ч» вместо «уже 4ч» (10 = 4 старых + уже вставленные этим же вызовом 6). Итог всё равно блокировался верно (10+6>8), но с неверными цифрами в сообщении. Исправлено — `check_daily_limit` теперь считается *до* вызова BAPI, а `APPEND LINES OF lt_limit_return TO lt_return` — после (иначе сообщения потерялись бы при внутреннем `REFRESH return` самой BAPI). Проверено вживую на PERNR 00099001: день с существующими 8ч + новая запись 1ч → блокирует с верными цифрами («уже 8.00 + новые 1.00 = 9.00»); пустой день + 8ч → проходит.
- ~~Нужен ли `cats_release`~~ — **решено 2026-09-22, подтверждено вживую.** Процедура утверждения в `TCATS` не настроена (`APPROVAL` пусто), поэтому `cats_release` сразу даёт статус `30` «Утверждено», без промежуточного `20`. Инструмент нужен — это единственный способ сдвинуть статус с `10`.
- ~~`cats_read`: параметр `status` объявлен в Node-схеме, но ABAP-маршрут `/read` его не использует~~ — **исправлено 2026-09-22.** `ts_read_request` дополнен плоским полем `status` (флет-массив), в `route_read` — range-таблица `tt_status_range` (`VALUE #( FOR ... ( sign = 'I' option = 'EQ' low = ... ) )`) и `IF ls_request-status IS NOT INITIAL` / `ELSE` с двумя вариантами `SELECT` (тот же приём, что уже применялся в `route_release` для `counters` — Open SQL `IN` с пустой range-таблицей вернул бы ноль строк вместо «без фильтра», а не то, что нужно). Транспорт — тот же, что у всего блока 3. Проверено вживую на PERNR 00099001: без фильтра — записи со статусами `10`/`30`/`60`; `status: ["30"]` — только одна запись (`30`); `status: ["30","60"]` — обе, без единой `10`.

## Правила работы в этом проекте

- **Транспорт не выбирать самостоятельно** — всегда спрашивать, какой запрос использовать, до любых операций записи в SAP.
- **Не трогать данные чужих табельных номеров без явного разрешения** — ни живыми пишущими вызовами (`cats_insert`/`cats_change`/`cats_delete`/`cats_release`), ни повторными read-only проверками (`cats_read`/`cats_validate`/`cats_capacity`) на чужом PERNR. Живые тесты — на своём табельном (в этом проекте — см. память проекта) или после прямого разрешения. Классификатор auto-режима иногда сам блокирует такие вызовы («PII Data Handling») — это ожидаемо, обходить не стоит.
- **Не писать поясняющие комментарии в ABAP-исходник** — объяснения идут в чат или в трекер.
- ABAP: локальные структурные типы с префиксом `ts_`, табличные — `tt_` сразу после своего `ts_`; `DATA(x) = VALUE ...` вместо голых блоков `DATA`; результат вызова функционального модуля объявлять заранее через `VALUE #( )`, не инлайном в `IMPORTING`; `LEFT JOIN` без слова `OUTER`; многострочные вызовы выравнивать по колонке.
- Общие классы и группы функций расширять **аддитивно**: новые необязательные параметры, не менять существующее поведение.
- **Снимать свои же блокировки ADT** в том же ходе, в котором поставил.
- Два `runQuery` в одном сообщении роняют сессию ADT-бриджа — запросы к БД идут строго по одному.
- Перед переводом задачи в «Тестируется» — опросник: оценка и дата проводки часов в CATS (в вариантах — ближайшие свободные дни по `cats_capacity`). Часы по оценке вносятся на выбранную дату через этот же MCP (`cats_validate` → `cats_insert` с `ext.ytr_key`) — флаг «Добавить в CATS» в Трекере это заменяет и больше не ставится.
- **Репозиторий публичный** (https://github.com/Hollway/mcp-sap-cats, с 2026-09-22) — в коммиты и документацию не должны попадать реальный хост/IP SAP, номера транспортов, табельные номера, логины и ФИО сотрудников. История уже была сквошена ради этого один раз, второй раз так удобно не будет — думать о публичности до коммита, не после.

These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
