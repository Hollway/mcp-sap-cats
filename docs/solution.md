# Техническое решение SAP-18862

Оформленная версия на согласование: https://claude.ai/code/artifact/f96144c4-e409-4855-a56f-1ce2a21f6300

Решения, факты о системе и подвохи профилей — в `CLAUDE.md`, контракт ICF-хендлера — в `handler-contract.md`. Здесь — требуемый ТЗ результат: перечень инструментов с параметрами, покрытие требований и оценка. Состояние на 2026-09-24: всё описанное реализовано и проверено вживую.

## Архитектура

```
MCP-клиент  →  MCP-сервер (Node)  →  HTTPS + Basic  →  ICF-узел /sap/bc/zcats  →  BAPI_CATIMESHEETMGR_*
```

- **Запись** — только через `BAPI_CATIMESHEETMGR_INSERT` / `_CHANGE` / `_DELETE`; фиксация (`BAPI_TRANSACTION_COMMIT` / `_ROLLBACK`) внутри того же HTTP-вызова. Проверки профиля, пользовательские выходы CATS и BAdI срабатывают так же, как в CAT2.
- **Чтение** — прямо из `CATSDB`: быстрее и отдаёт Z-поля без расширений.
- **Авторизация** — узел без сохранённых данных логона, каждый запрос идёт от имени реального пользователя. Запись проверяет сама BAPI по его полномочиям; чтение полномочий не проверяет (осознанное решение — читать можно любой табель).
- **Транспорт MCP** — stdio (сервер у каждого пользователя, логин в его `.env`) или HTTP (`MCP_TRANSPORT=http`, один сервер на всех). В HTTP-режиме логин SAP приходит от клиента заголовком `Authorization: Basic` в каждом запросе и передаётся в SAP без изменений, поэтому авторизация та же, что в stdio. Без сессий, TLS обязателен на любом адресе, кроме `localhost`.
- OData отклонён: стандартного сервиса для CATS в ERP нет. `node-rfc` отклонён: требует NW RFC SDK и нативной сборки за прокси.

## Структура записи

Объект `record` — в `cats_validate`, `cats_insert` и `cats_change` (у `cats_change` дополнительно `counter`).

| Поле | Тип | Куда в BAPI | Обяз. |
|---|---|---|---|
| `workdate` | дата `YYYY-MM-DD` | `WORKDATE` | да |
| `hours` | число, шаг 0,25 | `CATSHOURS` | да |
| `ext.prjct` | проект (активный) | `EXTENSIONIN` → `ZZPRJCT` | да, если нет `ext.ytr_key` |
| `ext.rqsnb` | номер ТЗ | `EXTENSIONIN` → `ZZRQSNB` | нет |
| `ext.ytr_key` | ключ задачи Трекера вместо пары проект + номер ТЗ | переводится MCP в `prjct` + `rqsnb` | нет |
| `ext.descr` | описание, до 35 символов | `EXTENSIONIN` → `ZZDESCR` | да, если нет номера ТЗ |
| `ext.orgunit` | оргединица | `EXTENSIONIN` → `ZZORGUNIT` | нет, SAP заполняет сам |
| `shorttext` | текст до 40 символов | `SHORTTEXT` | нет |
| `longtext` | подробный текст, до 4000 символов, с переводами строк | `LONGTEXT` (`BAPICATS8`) | нет |
| `receiver` | объект отнесения, ровно один вид | см. ниже | нет |
| `unit` | ЕИ, по умолчанию `STD` | `UNIT` | нет |
| `wagetype` | вид оплаты, по умолчанию `M120` | `WAGETYPE` | нет |
| `acttype` | вид работ | `ACTTYPE` | нет |
| `send_cctr` | МВЗ-отправитель | `SEND_CCTR` | нет |
| `start_time`, `end_time` | время `ЧЧ:ММ` | `STARTTIME`, `ENDTIME` | нет |
| `attendance_type` | вид присутствия/отсутствия | `ABS_ATT_TYPE` | нет |

Как в CAT2: при заданном номере ТЗ описание подставляет пользовательский выход CATS из названия ТЗ, без номера ТЗ описание вводят вручную — это правило проверяет схема MCP до вызова SAP. Неактивный проект отбраковывает выход CATS (`ZCATS001`).

Объект отнесения необязателен: существующий продовый код разнесения часов его не использует, и в этой системе записи с ним упираются в CO-кастомайзинг. Виды, если понадобятся:

| Вид | Форма | Поля BAPICATS1 |
|---|---|---|
| Заказ | `{ order }` | `REC_ORDER` |
| МВЗ | `{ cost_center, co_area }` | `REC_CCTR` + `CO_AREA` |
| СПП-элемент | `{ wbs }` | `WBS_ELEMENT` |
| Операция сети | `{ network, activity, sub_activity? }` | `NETWORK` + `ACTIVITY` |
| Заказ клиента | `{ sales_order, item }` | `RECSALEORD` + `RECITEM` |
| Заказ на закупку | `{ purchase_order, item }` | `PO_NUMBER` + `PO_ITEM` |

## Инструменты

Десять инструментов: семь по ТЗ, два справочных и сводка. Обязательные параметры помечены `*`. Пишущие и проверяющие инструменты возвращают `messages[]` — разобранный `BAPIRET2` (`type`, `id`, `number`, `text`, `row` — номер записи во входном массиве, `0` — весь вызов).

### `cats_whoami` — мой табельный номер

**Вход:** —
**Выход:** `user`, `pernr`, `name`, `orgeh`, `orgunit`

Табельный по пользователю SAP (ИТ 0105, подтип 0001), ФИО и оргединица из ИТ 0001.

### `cats_projects` — справочник проектов и номеров ТЗ

**Вход:** `search`, `prjct`, `ytr_key`, `limit` (50)
**Выход:** `projects[]` (prjct, text), `requests[]` (prjct, rqsnb, text, ytr_key, ytr_status, ytr_status_text, date_from, date_to, rejected), `projects_total`, `requests_total`

Без параметров — активные проекты; `prjct` — номера ТЗ проекта из старого графика разработок и из задач Трекера; `ytr_key` — пара проект + номер ТЗ для задачи Трекера; `search` — без учёта регистра.

### `cats_read` — вывод таймшита

**Вход:** `pernr*`, `date_from*`, `date_to*`, `status[]`
**Выход:** `rows[]` (counter, workdate, pernr, rec_cctr, rec_order, acttype, wagetype, unit, hours, status, status_text, rqsnb, prjct, descr, orgunit, longtext — признак подробного текста, longtext_text — сам текст), `total_hours`

`total_hours` не учитывает статусы 50 и 60 — сами строки выводятся.

### `cats_summary` — сводка по проектам и номерам ТЗ

**Вход:** `pernr*`, `date_from*`, `date_to*`, `by` (`request` — проект + номер ТЗ, `project` — только проект), `weeks` (false)
**Выход:** `groups[]` (prjct, rqsnb, descr, hours, days, records, by_status, weeks), `total_hours`, `days`, `by_status`, `weeks`

Считается на стороне MCP поверх `/read`, ABAP не меняется. Статусы 50 и 60 не входят, как и в `total_hours` `cats_read`. Записи без номера ТЗ группируются по проекту и описанию. Ключ недели — её понедельник. Проверено на реальных данных за месяц: итог совпадает с `total_hours` `cats_read`.

### `cats_capacity` — свободные часы по дням

**Вход:** `pernr*`, `date_from*`, `date_to*`, `norm_hours` (8)
**Выход:** `days[]` (date, is_workday, booked, free), `norm_hours`, `calendar`, `total_free`

Рабочие дни и праздники — по заводскому календарю `BY`. В нерабочий день `free = −booked`.

### `cats_validate` — проверка без сохранения

**Вход:** `pernr*`, `profile` (`TIME_D1`), `records[]*`, `norm_hours` (8)
**Выход:** `ok`, `messages[]`

BAPI с `TESTRUN = 'X'` проверяет записи по профилю, выходы CATS — проект; MCP добавляет дневной лимит. Ничего не пишет.

### `cats_insert` — создание записей

**Вход:** `pernr*`, `profile` (`TIME_D1`), `records[]*`, `idempotency_key*` (8–20 символов), `release` (false), `norm_hours` (8)
**Выход:** `created[]` (row, counter, workdate, hours), `committed`, `messages[]`

Несколько дней и проектов за один вызов. Повтор с тем же `idempotency_key` возвращает уже созданные записи, не задваивая часы. При любой ошибке вызов откатывается целиком.

### `cats_change` — изменение

**Вход:** `pernr*`, `profile` (`TIME_D1`), `records[]*` (каждая с `counter`), `test` (false), `norm_hours` (8)
**Выход:** `changed[]` (row, counter, workdate, status), `committed`, `messages[]`

Утверждённую запись (30) SAP правит новой версией: новый `counter` в статусе 10, старая запись уходит в 50. Записи в 50 и 60 менять нельзя (`LR162`). В лимите часы изменяемых записей заменяются новыми, а не складываются.

### `cats_delete` — удаление

**Вход:** `profile` (`TIME_D1`), `counters[]*`, `test` (false)
**Выход:** `deleted[]` (row, counter), `committed`, `messages[]`

Запись, которая ни разу не утверждалась (статус 10), SAP удаляет физически вместе с подробным текстом. Утверждённая запись (30) и новая версия, созданная её правкой, не удаляются, а переходят в статус 60 «Сторнировано».

### `cats_release` — деблокирование

**Вход:** `pernr*`, `counters[]` либо `date_from` / `date_to`
**Выход:** `released[]` (row, counter, workdate, status), `messages[]`

Берёт записи в статусе 10. Процедура утверждения в профилях не настроена, поэтому записи сразу получают статус 30 «Утверждено», а не 20. SAP при этом пишет свою строку-историю с нулём часов.

### Сценарии (MCP prompts)

`fill_week_like_last`, `fill_gaps`, `period_close_check` — собирают вызовы инструментов для типовых задач и ничего не пишут без подтверждения пользователя.

## Покрытие требований ТЗ

| Требование | Чем закрыто | Подтверждено |
|---|---|---|
| Вывод записей по сотруднику за период: дата, объект учёта, вид работ, часы, статус | `cats_read` | вживую, в т. ч. фильтр по статусам |
| Создание и изменение записей за период | `cats_insert`, `cats_change`, `cats_delete`, `cats_release` | вживую, полный цикл создание → изменение → деблокирование → сторно |
| Часы по нескольким дням и объектам за один вызов | `records[]` в одном вызове | вживую: 6 записей, 3 дня, 2 проекта |
| Проверка существования и доступности объектов учёта | `TESTRUN` в BAPI + выход CATS на активность проекта | вживую, построчные сообщения BAPI |
| Лимиты по часам в день | свой расчёт MCP (`norm_hours`), профили лимиты не проверяют | вживую, в т. ч. при изменении и после правки утверждённой записи |
| Закрытые / заблокированные периоды | в системе не настроены: CAT2 тоже пускает в прошлые периоды, BAPI окно профиля не проверяет | закрыто решением — отдельная проверка не нужна |
| Способ доступа | ICF-хендлер + BAPI, чтение из `CATSDB`; OData и `node-rfc` отклонены | — |
| Свои таймшиты либо подчинённых | запись — полномочия пользователя в BAPI (как в CAT2); чтение открыто решением | вживую: ввод за подчинённого проходит |
| Понятные сообщения об ошибках | разбор `BAPIRET2` с номером строки, свои тексты MCP | вживую во всех маршрутах |

Сверх ТЗ: идемпотентность записи, справочник проектов и номеров ТЗ, связка с задачами Трекера по ключу, подробный текст, сводка по проектам и номерам ТЗ (`cats_summary`), таймаут и автоповтор при блокировке записи, три сценария, HTTP-режим для общего сервера, автотесты (Node — 46, ABAP Unit — 17).

## Оценка

| Блок | Дней |
|---|---|
| Проверка гипотез через `TESTRUN` | 0,5 |
| ICF-хендлер и узел SICF | 1,0 |
| MCP-сервер, модель полей, инструменты | 2,5 |
| Идемпотентность | 0,5 |
| Разбор `BAPIRET2` | 0,5 |
| Тесты и приёмка | 1,0 |
| **Итого** | **6,0** |

Против `P1W` в ТЗ — на день больше. Разница: идемпотентность и разбор сообщений, которых в постановке не было. Четвёртый профиль ввода данных, который исходно выносился за оценку, не понадобился. `cats_summary` и HTTP-режим сделаны 2026-09-24 сверх ТЗ и в оценку не входят.

Отдельный инструмент со списком подчинённых не делается: требование «свои либо подчинённых» закрыто полномочиями пользователя в BAPI, как в CAT2 (решение 2026-09-23).
